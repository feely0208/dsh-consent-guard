# 用户同意与授权确认

查同意机制是否合规：**默认勾选、捆绑同意、没有撤回入口**。

## 一、判据来自法条，不是我们的偏好

| 项 | 依据 |
|---|---|
| **默认勾选** | 《个保法》第 14 条 —— 同意应「自愿、明确作出」；GDPR Recital 32 —— 预先勾选无效 |
| **捆绑同意** | 《个保法》第 16、17 条 —— 不得以不同意非必要处理为由拒绝服务 |
| **无撤回入口** | 《个保法》第 15 条 —— 个人有权撤回同意，处理者应提供**便捷**的撤回方式 |

**「默认勾选」在国内监管认定里通常是直接判违规的一项。**

## 二、它查什么

| 级别 | 项 |
|---|---|
| 🔴 高 | 同意勾选框默认勾选 |
| 🔴 高 | 采集个人信息但找不到同意/告知机制 |
| 🟡 中 | 同意与其他事项捆绑 |
| 🟡 中 | 找不到撤回同意的入口 |

## 三、怎么用

```bash
<cli 路径> --demo
<cli 路径> --list-rules
<cli 路径> --html r.html
```

## 四、边界

- **只看代码，不看实际界面** —— 「弹窗有没有真的弹出来」「用户能不能看懂」
  都要人工验证。本工具查的是**代码里写成了什么样**。
- **`CONSENT-NO-WITHDRAW` 和 `CONSENT-COLLECT-NO-BANNER` 是「找不到就报」**：
  - 撤回入口可能在服务端、或在 App 设置页（不在本仓库）
  - 同意机制可能在另一个仓库
  报出来是**提示你确认**，不是断定你没做。
- **只覆盖中国法 + GDPR 的常见要求**，不覆盖行业特殊规定（金融、医疗、未成年人）。
- **不判断「必要性」**：某项信息采集是否属于「提供服务所必需」是法律判断，
  本工具不做这个判断。

## 五、覆盖面

4 项，覆盖同意机制的「取得」与「撤回」两端。
